# R&S ESMD и EB500: протокол опроса

**Порт 5555 для ESMD подтверждён заказчиком.** Заказчик проверил на приборе: ESMD отвечает на `*IDN?` (SCPI по TCP работает). Команда `SYSTem:ERRor?` тоже проходит (подтверждено заказчиком, формат ответа не зафиксирован).

**EB500** (тоже в мониторинге): шаблон `templates/eb500_icmp_scpi.yaml` построен по руководству EB500, команды `*IDN?`, `*OPT?`, `SYSTem:ERRor?`, `SYSTem:ERRor:COUNt?` там описаны; на реальном приборе не проверены. Для обоих приборов используется один скрипт `esmd_check.py`.

## Что подтверждено источниками
- **Управление по LAN, SCPI.** Брошюра ESMD (R&S, v1001, 2019-07, [PDF](https://scdn.rohde-schwarz.com/ur/pws/dl_downloads/dl_common_library/dl_brochures_and_datasheets/pdf_1/ESMD_bro_en_5213-9863-12_v1001.pdf), с. 27): две LAN-карты 1 Гбит/с для удалённого управления и вывода результатов; «open interface description for remote control commands (in line with the SCPI standard)». Номер порта в брошюре не указан.
- **Описание команд ESMD в открытом доступе не найдено.** Страница ESMD на сайте R&S: прибор снят с производства (преемник R&S ESME); в Download Center для ESMD только брошюра и две статьи про TDOA, руководств (0), ПО (0). Руководство и ESMD-Control, возможно, за регистрацией Knowledge+ или выдаются по запросу в R&S/у поставщика.

## Что известно по родственному прибору (НЕ ESMD)
Руководство R&S EB500 (Operating Manual 4072.8426.02 v08, [копия](https://rigpix.com/rohdeschwarz/eb500_manual.pdf), гл. 4 «Remote Control via LAN»): SCPI 1993.0 по сырому TCP-сокету, **порт по умолчанию 5555**, проверка соединения командой `*idn?` (в Telnet), команда завершается переводом строки (LF), очередь ошибок `SYSTem:ERRor?`, порт настраивается командой `SYSTem:COMMunicate:LAN:PORT`.
Вывод: порт 5555 из памяти заказчика согласуется с семейством приборов R&S для радиомониторинга, но для ESMD это **аналогия, а не подтверждение**. Порты 5025/5125/4880/111/2525 (общие для R&S) для ESMD тоже не подтверждены.

## Как подтвердить на приборе (с ноутбука в одной сети)
1. `ping <IP>`; `Test-NetConnection <IP> -Port 5555` (PowerShell) - порт открыт?
2. Если нет - сканировать порты (nmap) и свериться с настройкой LAN в меню прибора/ESMD-Control.
3. Открыть сокет (PuTTY raw/Telnet), послать `*IDN?` + Enter: ожидается строка вида `ROHDE&SCHWARZ,ESMD,...`.
4. Проверить `SYSTem:ERRor?`, записать дословные ответы и сверить регулярные выражения модели/прошивки; затем включить триггер по модели в шаблоне ESMD.
5. Уточнить, не ограничено ли число одновременных соединений: опрос раз в 5 минут короткими сессиями, ESMD-Control/ARGUS на приборе не должны отваливаться.

## Запросы SCPI в шаблонах (только чтение)
| Команда | Назначение | Пример ответа | Где подтверждено | Прибор |
|---|---|---|---|---|
| `*IDN?` | идентификация, модель, прошивка | EB500: `ROHDE&SCHWARZ,EB500,<serial>, V<fw>-<id>` (ESMD: дословный ответ не зафиксирован) | ESMD: заказчик на приборе (ответ есть); EB500: руководство, гл. 4 | ESMD, EB500 |
| `SYSTem:ERRor?` | следующая запись очереди ошибок (чтение извлекает её из очереди) | `0, "No Error"` (EB500) | ESMD: заказчик (команда проходит, ответ не зафиксирован); EB500: руководство, SYSTem:ERRor? | ESMD, EB500 |
| `SYSTem:ERRor:COUNt?` | число непрочитанных записей очереди ошибок | число, напр. `2` | руководство EB500, SYSTem:ERRor:COUNt?; на ESMD не проверено, в шаблон ESMD не входит | EB500 |
| `*OPT?` | список установленных опций | `PS,IM,0,DF,HF,0,0,0,0,FE` | руководство EB500, общие команды IEEE 488.2 (*OPT?) | EB500 |

Не используются: `*TST?` (запускает самотест, скрипт его отклоняет) и любые команды, меняющие настройки: скрипт в режиме json принимает только запросы. Температура (`DIAGnostic:TEMPerature?`) и регистры STATus в шаблоны не включены: назначение точек измерения и биты не проверены на приборе.

## Структура шаблонов
Оба шаблона (`templates/esmd_icmp_tcp.yaml`, `templates/eb500_icmp_scpi.yaml`) устроены одинаково:
- простые проверки: ICMP, время ответа, TCP-порт (`{$ESMD.PORT}` / `{$EB500.PORT}`), триггеры недоступности;
- **один мастер-элемент** (EXTERNAL, TEXT, раз в 5 минут, таймаут 15 с, история 1 день):
  `esmd_check.py[json,{HOST.CONN},{$ESMD.PORT},"*IDN?","SYSTem:ERRor?"]` (EB500: `"*IDN?","*OPT?","SYSTem:ERRor:COUNt?","SYSTem:ERRor?"`). Одно TCP-соединение, один JSON; прежние отдельные raw-элементы удалены (прибору не нужны лишние соединения);
- **зависимые элементы** (DEPENDENT, JSONPath из мастера): `SCPI: отвечает` (1/0: соединение есть и получен хотя бы один ответ), `SCPI: команд с ответом`, `SCPI: время опроса`, идентификация, модель и версия прошивки (REGEX по `*IDN?`), последняя ошибка; для EB500 ещё опции и число записей в очереди ошибок;
- триггеры: «порт открыт, но SCPI не отвечает» (Average; `{$..PORT}` открыт и `SCPI: отвечает`=0 два опроса подряд); «есть записи в очереди ошибок» (Info, EB500; очередь содержит и безобидные ошибки команд, а чтение по одной записи за опрос её медленно разбирает); «модель не соответствует `{$ESMD.MODEL.MATCH}` / `{$EB500.MODEL.MATCH}`» (Info; **для ESMD выключен**, пока не подтверждён формат ответа `*IDN?`).
Если мастер не выполнился (ошибка скрипта, таймаут), зависимые элементы значений не получают; триггера на отсутствие данных нет.

## Ручная проверка
```
docker compose exec zabbix-server /usr/lib/zabbix/externalscripts/esmd_check.py json <IP> 5555 '*IDN?' 'SYSTem:ERRor?'
```
Вывод: один JSON (`tcp`, `answered`, `results`, `errors`, ...). Порядок и состав запросов должны совпадать с ключом мастера. Для EB500 добавить `'*OPT?' 'SYSTem:ERRor:COUNt?'`.

## Ручная проверка через VISA (подтверждено заказчиком)
Ресурс: `TCPIP0::<IP прибора>::5555::SOCKET` (сырой TCP, не VXI-11/INSTR).
Настройки: Termination Character = `\n` (LF), Termination Character Enabled = true, таймаут >= 5 с.
Команды: `*IDN?`, `SYSTem:ERRor?` (для EB500 дополнительно `SYSTem:ERRor:COUNt?`). Дословные ответы приборов в документ не внесены: уточнить и зафиксировать.

## Автоматическая проверка (CI)
`tests/test_esmd_check.py` (юнит-тесты `esmd_check.py`) и `tests/ci_scpi_e2e.py` (хосты ESMD и EB500 на фиктивном SCPI-приборе, принудительный опрос и проверка зависимых элементов) выполняются в CI. Это проверяет сам механизм опроса, не ответы реальных приборов.
